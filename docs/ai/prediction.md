# 예측 모델

모든 학습·검증 데이터는 **시뮬레이션**입니다. 결과는 “알고리즘이 시뮬레이터에 숨긴 규칙을 찾아내는가”이고, 1947 COMMONS 현장 정확도가 아닙니다. 재현: `npx tsx scripts/check-models.ts` (같은 계산을 `/ops`가 브라우저에서 다시 함).

## 시뮬레이터 가정 → `src/core/data/calibration.json`
모든 가정값(도착률, 일행 크기, 결제 방식, 키오스크 처리시간·기기별 속도, 조리 유형별 시간, 매장별 동시 조리 수)을 한 파일로 분리했습니다. 현장 측정값이 생기면 이 파일만 바꾸면 됩니다 → [calibration.md](calibration.md).

### 비현실적 값의 원인과 수정 (독립 검수 지적)
| | 이전 | 수정 후 (점심 피크, 7일) |
|---|---|---|
| 키오스크 1대 최대 줄 | 28명 | 12명 |
| 6대 합계 최대 | 134명 | 48명 |
| 준비시간 p80 최댓값 | 38.3분 (도쿄야), 27.8분 (경성카츠) | 10.6분 |
| 원인 | 피크 도착(분당 약 9건 결제)이 키오스크 6대 처리 용량(약 8건/분)을 40분 넘게 초과 → 줄이 계속 쌓임. 도쿄야는 동시 조리 2개에 조리 유형상 긴 메뉴. | 피크 도착 5.6→4.1팀/분, 폭 19→26분(덜 뾰족하게), 동시 조리 수 조정 |
- 상한(줄 14명/대, 합계 70명, 준비 p80 25분)은 `calibration.json`의 `plausibility`에 적고 단위 테스트(`src/core/sim/sanity.test.ts`)로 막습니다. 확인: `npx tsx scripts/sim-sanity.ts peak`.
- 기본 시연 시각은 그날 시뮬레이션에서 가장 붐비는 45분을 반복(`peakLoopStart`, 보통 11:40–12:40 사이). 실제 시각 연동은 선택(`?clock=real` 또는 체험 홈 토글).

## 키오스크 대기시간 (`predict/eta.ts`)
- 정의: 줄에 선 뒤 내 차례가 되어 화면을 누르기까지.
- 방법: 기기별 로그 처리시간을 경험적 베이즈로 전체 평균 쪽으로 당김 → 몬테카를로(앞선 결제 건수, 처리시간, 현재 이용자의 남은 시간) → p20–p80 표시.
- **카메라 인원 오차 반영(v3)**: 인원이 영상 AI에서 왔으면, 홀드아웃 합성 영상에서 측정한 집계 오차 분포(`src/core/data/count-error.json`)로 “실제 인원”을 표본 추출해 범위에 포함.

### 검증 (앞 4일 학습 → 뒤 2일 검증, 피크 시나리오)
2026-11-25 현장 메뉴 반영(메뉴 119→127개, 매장 순서 = 실제 키오스크 탭 순서)으로 시뮬레이션이 만드는 날이 바뀌어 같은 알고리즘의 수치도 움직였습니다. 알고리즘·파라미터는 바꾸지 않았습니다.

| 입력 / 방법 | MAE (현장 메뉴 반영 전 → 후) | p20–p80 적중 (목표 60%) |
|---|---|---|
| 모델 · 정확한 인원 | 25.3 → 28.1초 | 65% → 61% |
| 기준선 · 인원 × 전체 평균 · 정확한 인원 | 32.0 → 34.1초 | – |
| 모델 · **카메라 인원, 오차 무시** | 30.0 → 31.3초 | 59% → 58% |
| **모델 · 카메라 인원, 오차 반영 (적용)** | **28.0 → 30.6초** | **68% → 63%** |
| 기준선 · 인원 × 전체 평균 · 카메라 인원 | 37.1 → 38.1초 | – |
| 기준선 · 인원 × 이 기기 최근 중앙값 · 카메라 인원 | 33.6 → 34.1초 | – |

- 왼쪽 쏠림 시나리오(반영 후): 카메라 오차 무시 44.4초 → 반영 38.1초 (기준선 50.9 / 54.2초), 적중 59% → 70%.
- **한산한 날(반영 후): 카메라 인원 기준 모델 12.1초 vs 단순 기준선 11.2초 — 복잡한 모델이 낫지 않음.** 정확한 인원이면 8.8 vs 9.2초로 거의 같음. 줄이 거의 없을 땐 단순 계산과 같습니다.
- 데이터가 조금만 바뀌어도 MAE가 2–3초 움직인다는 점 자체가 “시뮬레이션 수치를 실제 정확도로 읽으면 안 되는” 이유입니다.

## 메뉴 준비시간 (`predict/prep.ts`)
- 한가할 때의 (브랜드, 조리 유형) 중앙값 + 앞선 주문 1건당 추가 시간 + 품목 수 보정. 구간은 실제/예측 비율의 20·80분위.
- 검증(피크, 현장 메뉴 반영 후): 모델 60.9초 vs 메뉴 평균 기준선 80.4초, 구간 적중 57% (반영 전 73.1 vs 80.3초, 60%). 한산한 날은 47.2 vs 47.8초로 차이가 거의 없음(밀린 주문이 적으면 기준선과 같아짐).

## 5–15분 혼잡 예측 (`predict/forecast.ts`)
- 후보 3개(현재값 유지 / 추세 감쇠 / 평소 패턴+현재 차이)를 하루씩 빼며 검증해 지평별 최선 선택.
- **구간 보정**: 10–90% 잔차 구간은 학습에 안 쓴 날에서 실제 적중 68–85%(목표 80%)였음 → 8–92%로 넓혀 **75–88%(평균 약 82%)**. 상수: `FORECAST_INTERVAL`.
- 재현: `npx tsx scripts/forecast-coverage.ts peak` (7일 중 하루씩 빼고 학습 → 뺀 날 검증).
- 현장 메뉴 반영 후(피크): 구간 적중 줄 83–84%, 자리 83–84%(목표 80%). 줄 인원 5/10/15분 MAE **4.7/5.0/5.3명 vs 현재값 유지 4.5/6.1/7.7명 — 5분 뒤 예측은 현재값 유지보다 조금 나쁨**(반영 전 3.6/3.8/4.2 vs 4.1/5.7/7.6). 10–15분은 계속 기준선보다 나음. 5분 지평을 현재값 유지로 바꿀지는 현장 데이터로 다시 정할 일이라 알고리즘은 그대로 뒀습니다.

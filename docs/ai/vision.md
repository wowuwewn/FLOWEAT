# 영상 인식 — v3 (2026-11-25, 독립 검수 반영)

> 모든 수치는 **테스트 영상**(실제 사람 이미지를 잘라 만든 합성 영상, 공개 영상) 기준입니다. 1947 COMMONS 실제 영상으로 검증하지 않았고, 실제 학식 성능을 주장하지 않습니다.

## 무엇을 바꿨나
- 독립 검수: “단순 구역(ROI) 인원 집계가 v2 추적 기반 집계보다 4개 시드 모두에서 대기 인원 MAE가 낮다”. **재현됨.**
- 원인 분석(완벽한 검출기 조건, `DETECTOR=oracle`): 검출이 완벽하면 v2 추적 기반이 가장 정확(MAE 0.034)했음 → v2의 약점은 로직이 아니라 **검출이 끊길 때 사람을 놓치는 것**(확정 트랙만, 1.2초 정지 후에만 셈).
- **v3 = 혼합(hybrid)**: 구역 안의 검출은 그대로 세되, 추적상 **걷고 있는 사람만 제외**, 0.4초 이내로 가려진 대기자는 유지, 1초 중앙값으로 흔들림 감소. 주문 중 표시는 ‘키오스크 앞에 서 있는 사람’(검출 기반), 처리시간 측정은 추적 기반 기록 유지. 코드: `src/core/vision/analysis.ts` (`QueueMode`), 기본값 `hybrid`.
- 합성 영상 생성기 오류 수정: 재생 데이터 행이 7필드로 바뀐 뒤 `ValueError: too many values to unpack` → 수정. 사람 이미지 원본 상자를 고정 픽스처(`data/fixtures/sprite_tracks.json`)로 분리해 **같은 시드 = 같은 영상**(시드 1947 재생성 결과가 기존 정답과 프레임 단위로 일치).

## 평가 설계 (재현 방법)
```bash
VIDEO_DIR=data/videos scripts/vision/make-synth-set.sh dev       # 개발 시드 1947, 7, 2027, 31 (×정면/비스듬히)
VIDEO_DIR=data/videos scripts/vision/make-synth-set.sh holdout   # 홀드아웃 시드 4242, 8080, 1203, 555
npm run vision:bench -- dev        # 검출 결과 캐시 후 세 방식 비교 → docs/ai/evaluation/queue-bench-dev.json
npm run vision:bench -- holdout    # 알고리즘 고정 후 한 번만 → queue-bench-holdout.json
DETECTOR=oracle npm run vision:bench -- holdout   # 완벽한 검출기(로직만의 오차)
```
- 원본 영상: Intel IoT DevKit sample-videos `one-by-one-person-detection.mp4` (CC BY 4.0)을 `data/videos/`에.
- **결정 규칙(개발 세트에서, 홀드아웃 전에 확정)**: 통행자를 대기로 세는 비율 ≤ 10% 중 MAE 최소. 파라미터 탐색(유지 프레임·중앙값 창·걷기 속도·검출 점수 48+4조합)은 개발 세트에서만, 홀드아웃 파라미터 변경은 코드로 막음. 고정 커밋: `1e000ac`.
- 지표: 대기 인원 MAE, 과다 집계 비율, 평균 과소 인원, **통행자 오인**(통행자가 줄 구역에 있을 때 대기를 정답보다 많이 센 비율), 주문 중 판정 정확도, 이용 기록 매칭, 처리시간 오차, 잘못 잡은 이용 기록.

## 테이블 — 실제 영상과 단위 테스트를 구분
- 공개 실제 영상(`classroom.mp4`): 이용할 수 없는 자리를 빈자리로 보여 준 경우 1/64칸. **이 영상엔 실제로 비워진 테이블이 없어 ‘빈자리 찾기’ 정확도는 측정 불가.**
- 비운 자리 → 빈자리 전환, 가방 = 맡은 자리, 그릇만 = 판단 어려움, 가림 처리는 **단위 테스트(가상 검출 입력)로만** 확인. 실제 정확도로 표기하지 않음.

## 앱에서 쓰는 방식
- 학생 앱 기본은 시뮬레이션. ‘영상 AI 결과 연결’을 켜면 **왼쪽 키오스크 3대**(합성 영상 v3 재생)와 **중앙 칸막이석 4개**(공개 영상 재생)만 영상 분석값으로 바뀌고 ‘영상 AI’ 표시가 붙음. 카메라로 센 인원은 측정된 집계 오차를 반영해 대기시간 범위를 계산(`docs/ai/prediction.md`).
- 데이터 종류 표기: 시뮬레이션 / 테스트 영상 AI 분석 재생(서버에서 미리 추론) / 이 브라우저 실시간 추론.

- 정면 카메라에서는 가운데 줄이 카메라 축과 겹쳐 **앞사람이 뒷사람을 완전히 가린다** → 3명이 1개 상자로 합쳐짐. 분석 로직으로는 해결할 수 없는 배치 문제라 **줄을 옆에서 비스듬히(약 40–50°) 보는 위치를 권장**한다.
- 가장 가까운 줄(L3)은 비스듬한 카메라에서도 대기 오차가 남는다(사람이 크게 겹침). 실제 설치 시 줄 2–3개당 카메라 1대 또는 높이를 더 올리는 안을 검토.
- 관측 대기시간(줄에 선 순간 → 주문 시작)은 사람이 걸어 들어올 때 ID가 끊겨 표본이 적고(4건) 오차가 크다. 그래서 **예측에는 이용 시간을 쓰고**, 관측 대기시간은 참고값으로만 기록한다.

Tiny 비교: 비스듬한 카메라 대기 오차 0.596명으로 Nano(0.633)보다 조금 낫지만 추론 31.6ms로 2.5–3배 느리고 5.5배 커서 기본은 Nano 유지.

## 테이블 (공개 영상, 재라벨)
v1 보고서의 "빈 테이블 8건 중 빈자리 판정 0건"을 1초 단위로 다시 확인했다. 8건 모두 **자리 주인이 테이블 바로 옆에 서 있거나(노트북을 두고) 잠깐 일어난 뒤 다시 앉는 장면**이었다. 즉 이 영상에는 실제로 비워진 테이블이 없다.
- 라벨을 3분류(앉음 / 맡음·잠깐 비움 / 비어 있음)로 다시 정의: `data/labels/tables.json`.
- '이용할 수 없는 자리를 빈자리로 보여 준' 경우: **1/64칸** (사람이 다시 앉는 순간 1칸).
- 실제로 비워진 자리를 찾아내는 능력은 이 영상으로 검증할 수 없어서, 단위 테스트(`src/core/vision/analysis.test.ts`)로 검증: 비운 자리 → 약 4초 안에 비어 보임, 가방 → 맡은 자리, 컵만 → 판단 어려움 후 치우면 비어 보임, 지나가는 사람 가림 → 상태 유지, 오래 가림 → 판단 어려움, 1인석 독립.
- 실영상 검증은 [촬영 가이드](../demo/filming-guide.md)의 B4(실제로 비우기) 장면으로 진행한다.

# (이전 기록) 영상 인식 v1 — 2026-11-24

## 파이프라인

1. **검출**: YOLOX(ONNX, 416×416). 사람과 물건 단서(가방·컵·그릇·병·노트북·휴대폰·책)만 사용. BGR, 0–255, 패딩 114, 정규화 없음 → 그리드 디코딩 → 클래스별 NMS(0.45).
2. **추적**: ByteTrack-lite — 등속 예측, 높은 점수(≥0.5)·낮은 점수(0.25–0.5) 2단계 IoU 매칭, 2회 연속 검출 시 확정, 8프레임 놓치면 삭제. ID는 짧게 쓰고 신원과 연결하지 않음.
3. **구역 판정** (`src/core/vision/analysis.ts`, 기준점 = 발 위치)
   - 이용 중: 이용 구역에 1초 이상 → 이용 시작. 1.5초 비면 종료, 3초 이상이면 이용 기록 저장 → 처리속도 계산 입력.
   - 대기: 대기 구역에 2초 이상, 속도 < 프레임 폭 8%/초. 지나가는 사람은 제외해 따로 셈.
   - 테이블: 좌석 영역 + 사람 크기 + "앉은 머리선" 아래일 때 착석. 사람 3초 내 → 사용 중, 물건만 → 판단 어려움, 8초 유지 후 빈자리, 서 있는 사람에 가려지면 판단 어려움.
4. **출력**: 집계값만(이용 여부, 경과 시간, 대기 인원, 테이블 상태). 영상·얼굴·개인 기록은 저장·전송하지 않음.

## 모델 비교 (2026-11-24, `docs/ai/evaluation/vision-latest.json`)

| | YOLOX-Nano (기본) | YOLOX-Tiny |
|---|---|---|
| 라이선스 | Apache-2.0 | Apache-2.0 |
| 크기 | 3.7MB | 20.2MB |
| 키오스크 이용 판정 정확도 (70프레임) | 85.7% | 84.3% |
| 사람 수 MAE | 0.10 | 0.11 |

| 사용 중 → 빈자리 오표시 (64칸) | 0% | 0% |
| Node CPU 추론 (4코어) | 11–25ms | 30–48ms |
| 브라우저 WASM 4스레드 (헤드리스 Chromium) | 약 48ms | 측정 예정 |

- 이용 판정 오류는 대부분 다가오는·떠나는 1–2초 구간(1초 체류 규칙의 의도된 지연).
- 비어 있던 테이블 8칸 중 4칸은 "판단 어려움", 4칸은 8초 유지 규칙으로 "사용 중" — 잠깐 일어난 사람의 자리를 빈자리로 보이게 하지 않으려는 설계.
- **라벨은 Claude Code가 2초 간격 프레임을 육안으로 표시한 것**(`data/labels/`)이라 팀원 검수가 필요합니다. 테스트 영상은 실제 학식이 아니므로 현장 정확도로 주장하지 않습니다.

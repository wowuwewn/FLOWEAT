### 한 문장 소개

FLOWEAT은 AI로 학식의 키오스크 대기와 테이블 혼잡을 인식하고, 브랜드·메뉴별 준비시간을 예측해 학생이 어디에서 주문할지 판단하도록 돕고, 주문 후에는 QR을 통해 음식 완료 알림과 수령 위치를 제공하는 단국대 학식 내비게이션이다.

### 우리가 줄이려는 것은 무엇인가

- 줄 길이와 처리 속도를 비교하기 어려워 발생하는 비효율적인 줄 선택.
- 메뉴가 얼마나 늦게 나올지 모르는 불확실성.
- 공용 모니터 앞 대기, 주문번호 반복 확인 및 이동.
- 만석 여부를 모르고 식당을 방문하거나 음식을 주문하는 상황.

좌석을 새로 만들거나 식사 시간을 강제로 분산하는 서비스가 아니다. 실제 총대기시간 또는 학식 전체 혼잡도가 감소하는지는 실험 결과에 따라 판단한다. 특히 실제 만석일 때는 상태 인식까지만 제공할 수 있음을 명확히 한다.

## 2. 현장 이해와 근거

### 2.1 공식 자료에서 확인한 시설 정보

학교의 2025년 개관 안내에 따르면 죽전 1947 COMMONS는 1,505㎡ 규모, 최대 600명 이용 가능 공간이며, 개장 당시 음식 매장 10개와 카페 1개가 입점한 푸드코트 형태이다. 이는 개장 자료 기준이며, 현재 좌석 수·정확한 테이블 수·최신 입점 명단으로 단정하지 않는다. 천안캠퍼스의 동명 시설과 혼동하지 않는다.

### 2.2 학생이 직접 제공한 현장 관찰

아래 내용은 사용자 본인의 경험과 설명이다. 학교 전체의 계량 조사 결과가 아니다.

| 구분 | 관찰 및 기획 반영 |
|---|---|
| 키오스크 | 총 6대. 정문 기준 왼쪽 3대, 오른쪽 3대. 각 기기별 개별 줄. 모든 기기에서 동일 메뉴 주문 가능 |
| 키오스크 식별 | 실제 기기에 번호 표시 없음. 번호가 아닌 입구 기준 위치와 배치도를 활용 |
| 배치 방향 | 좌우 키오스크에 각각 바깥쪽으로 대기열이 이어지는 형태. 기기와 줄의 상대적 방향은 사용자 확인. 전체 평면·정확한 간격·출입 동선은 미확정 |
| 주문 대기 | 피크에 사람이 많으면 각 줄 길이 비교 어려움. 가까운 줄에 서기 쉽고, 앞사람의 메뉴 고민이나 여러 건 주문으로 짧은 줄이 더 느린 경우도 자주 경험 |

| 공용 모니터 | 약 2~3대, 여러 브랜드의 완료된 번호를 표시. 조리 중 진행률은 표시하지 않음 |
| 완료 처리 | 직원이 완료 버튼을 누르면 모니터에 표시되는 것으로 추정. 실제 이벤트 연결 방식은 운영자/업체 확인 필요 |

| 좌석 | 점심에는 실제 만석이 주된 문제이고, 빈 테이블이 생겨도 거의 즉시 채워짐. 주로 분리 불가능한 4인용 테이블, 낯선 학생끼리 합석은 드묾 |
| 자리 선점 | 주문 전 가방 등으로 자리 맡기와 주문 후 자리 찾기가 섞여 있음. 음식을 들고 기다린 경험과 자리 탐색 중 완료번호를 놓친 경험이 있음 |
| 대기 공간 | 일부 있으나 점심 피크에는 대부분 혼잡. 포장 불가, 별도 식사 공간 없음 |
| 메뉴 정보 | 학교 앱에 있지만 주변 학생들은 잘 쓰지 않는다는 관찰. 현장에서는 키오스크만으로 메뉴 확인. 품절은 거의 경험하지 않음 |
| 카메라 | 기존 설치 확인은 했지만 수량·각도·영상 접근권한 미확인. 몇 대로 주요 테이블을 관찰할 수 있을 것으로 추정 |
| 사용 의향 | 사용자 본인은 완료 알림을 위해 앱 설치 의향도 있고 학식 방문 전·이동 중 혼잡/메뉴 정보를 확인할 의향도 있음. 다른 학생에 대한 일반화는 검증 필요 |

카메라 ROI(분석할 영상 영역), 기기 위치, 대기 방향, 수령대, 좌석 구역은 별도의 설정 데이터로 관리한다. 실제 자료가 확보되면 UI 재개발 없이 배치를 교체할 수 있도록 권장한다. 내부 ID는 `L1~L3`, `R1~R3` 등을 써도 되지만 실제 기기에 해당 번호가 붙은 것으로 학생 화면에 표시하지 않는다.

### 2.4 입점 브랜드 및 메뉴

- 사용자 현장 확인: **비비고고, 가오슝**.
- 이전 조사에서 수집한 참고 후보: 값찌개, 경성카츠, 바비든든, 포포420, 광뚝, 폭풍분식 등. 이번 작성 시 운영사 브랜드 페이지 직접 접근이 되지 않아 현재 죽전점 입점 여부는 재확인 대상이다.
- 최신 전체 명단·메뉴명·가격·사진·운영 시간·수령대 위치는 학교 앱, 실제 메뉴 화면, 운영사 자료로 확정한다. 후보 브랜드를 전체 현재 입점 목록으로 표기하지 않는다.
- 확인 전에는 실제 확인된 브랜드를 중심으로 시제품을 구성하고, 시연용 추가 브랜드·메뉴·가격·예상시간은 예시임을 표시한다. 메뉴가 많아도 무리 없이 데이터 추가가 가능한 구조로 설계한다.

## 3. 핵심 차별성 및 제품 전략

### 대표 기능: AI 대기열 내비게이션

사용자가 눈으로 비교하기 어려운 6개 개별 줄의 상황을 실제 배치 기반 화면에서 파악할 수 있게 하고, 인원수뿐 아니라 최근 주문 처리 속도를 반영해 예상 대기 범위를 비교한다. 가장 짧은 줄이 항상 가장 빠르지 않다는 현실을 반영한다. 학생에게 선택권을 제공하며 줄을 강제 배정하지 않는다.

### 반복 사용 구조

- **방문 전:** 현재 학식 상태 + 가까운 미래의 혼잡 변화 + 브랜드·메뉴별 준비 예상시간을 확인.
- **현장:** 실제 배치 기반으로 키오스크 대기 비교. 기존 주문 유지.
- **주문 후:** 번호표 QR 스캔으로 내 주문을 연결하고 완료 알림을 받는다. 여러 브랜드 주문은 한 화면에서 각각 확인 가능.

세 단계의 상황은 데이터 구조와 화면의 정보 구분에 활용하되, 학생에게 불필요한 '세 가지 혼잡 원인 분석'을 강요하지 않는다. 생성형 AI가 인과관계나 정확한 대기시간을 지어내지 않도록 한다.

### 경쟁 서비스와의 관계

- YAMMI(야미): 학식 예약·결제·조리 알림·시간/메뉴 분산 기능을 이미 제공한다. FLOWEAT은 기존 키오스크 주문을 유지하면서 실제 기기별 줄과 테이블 상태를 제공한다는 설계 차이가 있다.
- Waitz: 실시간 공간 혼잡 정보 제공. FLOWEAT은 학식 현장의 주문 대기열 비교, 브랜드별 준비 예상, 개인 주문 완료까지 이어지는 사용자 여정에 집중한다.
- 이 서비스는 세계 최초의 혼잡도 앱 또는 유일한 주문 알림 기술이라고 주장하지 않는다. 경쟁사의 공개 자료에서 확인되지 않는 기능을 '없음'으로 단정하지 않는다. 차별성은 실제 1947 COMMONS 구조에 맞춘 통합 경험과 검증된 사용자 가치로 입증한다.

### 제외 범위 (확정)

- 모바일 주문·결제, 무제한 주문 유입, 원격 줄서기·대기 등록·좌석 예약/배정, 강제 식사시간 분산.
- 포장, 합석 강요, 테이블 분리, 존재하지 않는 추가 식사 공간 활용, 좌석 선점·빈자리 푸시 알림, 개별 빈 테이블 확보 보장.
- 별도 친구 추가/그룹 생성, 음식 동시 조리 강제, 시간표 연동, 다음 수업까지 남은 시간/식사시간/강의실 이동시간 계산, 별도 AI 챗봇.
- 품절 중심 기능, 실사용자 결제·학생 개인정보 수집, 새로운 입구 전광판 설치, 도서관·셔틀·카페 등 추가 시설의 이번 구현.
- 기존 직원에게 별도 완료 입력을 반복 요구하는 운영 방식.

품절·메뉴 판매 여부는 공식 데이터가 있는 경우 일반 메뉴 상태로만 처리할 수 있다. 기능 추가를 의미하지 않는다.

## 5. 사용자 경험 및 화면 요구사항

### 5.1 학생의 정상 흐름

1. 강의실에서 출발하기 전, 이동 중 또는 정문에서 홈을 연다. 로그인/시간표 입력 없이 혼잡과 메뉴를 확인한다.
2. 키오스크 배치 화면에서 좌우 3대의 예상 대기를 비교한다. 번호가 없는 현장과 일치하도록 위치 중심으로 안내한다.
3. 브랜드를 선택하거나 메뉴를 검색해 예상 준비시간을 비교한다. 별도 시간 계산 입력을 요구하지 않는다. 키오스크에서는 기존 메뉴 선택에 준비시간 한 줄만 추가하는 방향을 우선한다.
4. 현장 키오스크에서 기존과 같이 주문한다(데모는 모의 결제). 여러 브랜드를 주문했다면 각각의 번호표와 QR이 발급된다.
5. 휴대폰 카메라 또는 앱 내 스캐너로 QR을 읽어 해당 주문을 연결한다. 다시 스캔해도 중복 등록되지 않는다. 주문 추적 전용 페이지는 불필요한 회원가입 없이 열 수 있어야 한다.
6. 주문을 기다리며 모니터에 갈 필요 없이 상태를 확인한다. 현재 테이블 혼잡은 참고로 볼 수 있다. 실제 완료 이벤트 이전에 준비 완료를 표시하지 않는다.
7. 직원이 완료 처리하면 해당 브랜드 주문만 완료 상태와 알림을 받는다. 브랜드명·주문번호·수령 위치(확인된 경우)와 최신 혼잡 상태를 보여준다. 다른 주문은 대기 상태를 유지한다.
8. 음식 수령 후 추적을 종료하거나 주문이 만료된다. 실제 수령 데이터가 없다면 자동으로 수령 완료했다고 주장하지 않는다.

### 5.3 오류 및 접근성

모바일 우선, 실제 iOS/Android에서 주문 추적이 가능해야 한다. 글자·색상 대비, 키보드 접근, 큰 터치 영역, 색상 외 상태 텍스트, 모션 감소 설정, 로딩·오프라인·지연·데이터 없음·알림 거부·잘못된 QR·만료 상태를 포함한다. 지원되지 않는 알림은 대체 경로를 명확히 안내한다. 기존 키오스크 접근성 기능을 해치지 않는다.

## 6. AI 및 시스템의 핵심 구현 요구사항

### 6.1 카메라 대기열 인식과 예상 주문 대기시간

- 6개 기기의 대기 영역을 실제 영상과 연결한다. 필요 시 기기 이용 중 영역, 통행 영역, 대기 영역을 구분한다. 기존 CCTV의 시야는 확인 전제이지 확보된 입력이 아니다.
- 객체 검출과 단기 위치/움직임 추적을 사용해 사람 수를 추정한다. 얼굴 식별, 개인별 프로필 생성, 학생 추적 이력 저장은 하지 않는다. 줄을 지나가는 사람, 함께 기다리지만 주문하지 않는 사람, 가림 및 줄 겹침은 불확실 요인이다.
- 기기별 최근 처리 간격, 관측된 줄 감소 속도, 이용 중인 주문의 남은 시간 추정, 대기 인원에서 추정한 주문 건수를 조합한다. 사람 수와 주문 건수는 같다고 가정하지 않는다.
- 예측 정의는 '현재 해당 줄에 합류한 후 주문을 시작하기까지의 예상 대기'를 권장한다. 결제 완료까지 추정한다면 이를 별도 라벨로 표시하고 일관되게 평가한다.
- 기준선 예시: 앞선 예상 주문 건수 × 최근 기기별 처리시간 분포 + 현재 주문의 예상 잔여시간. 기기별 중앙값·분위수와 표본 부족 시 공통 기준선으로 보완. 추정 범위를 제공하고 정확한 시각을 보장하지 않는다. Claude Code가 더 좋은 추정 모델을 제안할 수 있다.
- 예시: 인원은 왼쪽 줄이 적어도 오른쪽의 최근 처리 속도가 빠르면 오른쪽의 예상시간이 짧을 수 있다. 이 차이가 실제로 계산되어 UI에 드러나야 한다.
- 모든 학생을 한 기기로 유도하지 않도록 6대 정보를 동시에 제공한다. 예상시간 차이가 오차 범위 안이면 '비슷함'으로 표시하고, 특정 줄 추천 푸시나 강제 이동은 금지한다. 급격한 상태 변화와 갱신 시각을 반영한다.

### 6.2 테이블 점유와 실시간 혼잡 인식

- 테이블 위치/구역을 영상 영역에 매핑하고 사람·가방 등 관측 가능한 단서로 상태를 추정한다. 사전학습 검출 모델이 가방/선점까지 완벽하게 구분한다고 가정하지 않는다.
- 상태 모델 후보: `occupied`(사용 중), `apparently_empty`(비어 보임), `uncertain`(가림, 물건 선점 불명확, 미관측 등). 선점되었다고 확실히 판단된 테이블은 점유 상태로 간주하고 불확실하면 별도 분류한다.
- 테이블 점유율과 의자 점유율은 서로 다른 지표다. 사용 가능한 모든 테이블을 관측하지 못할 경우 관측 영역 기준의 수치를 명시하고 미확인 수량을 별도로 표시한다. 불확실 테이블을 모두 빈자리로 간주하지 않는다. 필요하면 점유율 범위와 관측률을 함께 표시한다.
- 학생에게는 구역별 혼잡 상태와 최근 관측값을 보여준다. 실제로 빈 테이블이 생기면 곧 차는 상황을 반영해 정확한 빈 테이블 확보나 위치 푸시를 하지 않는다.
- 목표는 상황 인지와 탐색 불편 개선이다. 물리적인 만석을 없앤다는 기능이 아니다.

### 6.3 브랜드·메뉴별 준비시간 예측

- 정의: 키오스크 주문 접수 후 해당 브랜드 주문의 완료 처리까지 걸리는 시간. 키오스크 줄, 식사 시간, 착석 대기는 포함하지 않는다.
- 브랜드/조리 코트의 작업량, 현재 미완료 주문 수, 메뉴별 조리 특성, 주문 품목 수, 접수/완료 이력, 시간대를 입력 후보로 삼는다. 브랜드 내부 메뉴의 조리 자원 공유 여부는 데이터로 확인한다.
- 초기에는 메뉴×시간대 또는 브랜드별 경험적 중앙값/분위수 기반 예측과 작업량 보정으로 시작할 수 있다. 실제로 계산하고 변화된 입력에 반응해야 한다. 충분한 표본으로 검증 가능하면 회귀/시계열 등 머신러닝 모델을 비교한다.
- 표본이 부족하면 브랜드 수준 범위 또는 '정보 부족'으로 표시한다. 브랜드 준비시간은 여러 메뉴의 요약임을 분명히 하고, 개별 메뉴 정확도와 동일하다고 간주하지 않는다. 가상 기록으로 계산한 값은 시뮬레이션으로 표시한다.
- 주문 후에 남은 예상시간을 제공할 경우 단순히 초기값에서 시간을 빼서 실제 완료처럼 처리하지 않는다. 직원의 실제 완료 신호가 우선한다.
- 빠른 메뉴로 수요가 몰려 처리시간이 달라지는 상황을 업데이트에 반영한다. 메뉴를 강제로 변경시키지 않는다.

### 6.4 단기 혼잡 예측 (고도화)

- 방문 예정 학생을 위해 현재 상태와 약 5~15분 뒤 상태를 구분해 제공한다. 식사 시간을 바꾸라는 기능이 아니다.
- 가능한 입력: 최근 대기열/테이블 점유 스냅샷, 유입·이탈 변화, 주문 접수/완료 추이, 시간대와 요일. 개인 시간표는 필요하지 않다.
- 기준선 예시: 현재값 유지 또는 최근 변화량을 이용한 단기 추정. 충분한 시계열을 확보하면 더 나은 모델과 비교한다. 인원과 점유율의 물리적 범위를 지키며 예측 구간과 예측 범위를 표시한다.
- 반복적인 점심 피크 패턴을 확인하지 못했거나 검증 데이터가 부족하면 '예측 정보 부족'으로 표시하고 관측된 추이만 제공한다. 사전 생성한 가상 곡선을 실제 AI 예측이라고 발표하지 않는다.
- 개별 키오스크 줄의 단기 변화가 너무 불확실하면 전체 주문 대기·테이블 혼잡 변화부터 검증한다. 범위와 모델 선택은 계획 단계에서 제안한다.

### 6.5 생성형 AI 적용 원칙

공모전 공식 목적은 생성형 AI를 활용한 대학생활 AX 솔루션 기획·개발이며, 팀 결과물은 생성형 AI·바이브코딩으로 만든 작동형 콘텐츠이다. 컴퓨터 비전과 통계 예측 자체는 생성형 AI가 아니다.

- Claude Code/Codex 등으로 문제 해결 과정을 구현한 기록과 검증·수정 내용을 남긴다. 개발 도구 활용만으로 서비스 내 생성형 AI 요건이 충족된다고 단정하지 않는다.
- 서비스 내부 적용안으로 구조화된 실제 상태/추정 데이터의 짧은 상황 안내(필요 시 자연어 설명)를 권장한다. 예: '왼쪽 안쪽과 오른쪽 입구 쪽의 예상 대기가 비슷하고, 찌개 메뉴는 준비시간이 길어졌어요.' 고정된 장문 브리핑 화면·별도 챗봇·억지로 원인을 만들어내는 기능은 제외한다.
- 에이전트는 위 방법보다 실질적이고 간결한 생성형 AI 적용안을 제시할 수 있다. 단순 요약은 규칙으로도 가능한 만큼 사용자 가치와 공모전 적합성을 검토한 후 채택한다. 런타임 적용이 곤란하다면 그 이유와 공식 요구사항 충족 근거를 계획에 명확히 기재한다.
- 생성형 AI를 적용하는 경우 서버에서 검증된 숫자·상태·모드·갱신 시각만 전달한다. 없는 사실이나 수치, 착석 보장, 인과관계 생성 금지. 구조화된 출력과 검증/규칙 기반 대체, 의미 있는 상태 변화 시 캐싱, 비용·오류·지연 제한을 적용한다.

## 7. 주문, QR 및 이벤트 설계

### 필수 관계

`모의 결제/주문 묶음 1개 → 브랜드별 주문 N개 → 각 주문의 고유 조회 QR → 해당 브랜드의 완료 이벤트 → 공용 모니터 및 학생 주문 상태`

- 표시용 번호와 서버의 고유 주문 ID는 분리한다. 표시 번호가 재사용·중복될 수 있어 주문번호 문자열만으로 개인 주문을 조회하지 않는다.
- 동일한 결제에서 여러 브랜드가 포함되면 브랜드별 주문을 생성한다. 각 QR은 해당 주문에 접근할 수 있는 추측하기 어려운 만료 가능한 조회 토큰을 담는다. 결제·개인정보를 넣지 않는다. 추가로 묶음 QR이 더 유용하다면 선택안으로 제안하되 필수 범위가 아니다.
- 여러 QR을 스캔한 학생은 자신의 기기에서 등록된 주문을 함께 볼 수 있다. 친구 그룹 기능이나 회원 간 주문 공유를 만들지 않는다. 다른 사람의 주문표 QR은 본인이 허락해 공유한 경우에만 등록한다. 공용 번호표 숫자로 타인의 개인 주문 페이지를 열 수 없어야 한다.
- 최소 상태: `accepted`, `ready`, `expired/closed`. 실제 조리 시작 이벤트가 없는 경우 임의의 '조리 중 70%' 등을 표시하지 않는다. 수령/종료는 실제 수령 이벤트 또는 사용자 종료 동작과 구분한다.
- 모의 직원 화면은 해당 브랜드 주문을 조회하고 완료 상태로 전환한다. 완료 이벤트는 한 번만 유효하도록 멱등 처리하고, 재접속 시 최신 상태를 조회한다.
- 공용 모니터는 기존처럼 완료된 번호를 표시한다. 앱 미사용 학생도 기존 방식 그대로 이용할 수 있다.
- 모바일은 완료 이벤트를 실시간 수신한다. 화면이 열린 상태의 알림은 P0 필수. 실제 백그라운드/잠금화면 알림은 PWA/네이티브·기기 조건과 권한을 고려하고, 특히 iOS에서 실제 기기 검증 후 제공 범위를 확정한다. 단순 QR 웹페이지가 닫힌 뒤에도 자동으로 푸시가 오는 것으로 표현하지 않는다.
- 예측된 시간이 지나도 완료 처리 전까지는 준비 완료 알림을 보내지 않는다. 이미 완료된 주문 QR을 열었을 때는 현재 완료 상태를 즉시 표시한다.

## 8. 구현 구조 및 기술 선택의 자유

특정 프레임워크, 데이터베이스, 디자인 도구 사용은 강제하지 않는다. Claude Code는 기존 저장소/환경, 팀 기술 역량, 공모전 일정, 모바일 알림, 실제 비전 분석의 실행 환경, 공개 데모 안정성, 비용 및 라이선스를 고려해 최적안을 제안한다.

### 권장 구성 예시 (교체 가능)

- 학생/키오스크/직원/모니터 웹: React/Next.js + TypeScript 또는 동등한 기술. 모바일 우선, 앱처럼 동작하는 UX. PWA 또는 앱 확장 검토.
- API·데이터·실시간 동기화: Supabase/Postgres/Realtime, FastAPI 또는 동등한 스택. 서버가 상태 변경의 기준이고 실시간 이벤트 또는 SSE/WebSocket/폴링 대체 지원.
- 영상 분석: Python + OpenCV + 사전학습 객체 검출 모델(예: YOLO 계열) 또는 적합한 대안. 영상 분석을 실제 수행하는 워커 환경을 분리하거나 합리적으로 통합한다. 정적 웹 배포가 GPU/영상 추론까지 제공한다고 가정하지 않는다.
- 예측: 검증 가능한 통계 기준선부터 구축, 실제 데이터가 충분할 때 학습 모델 비교. 생성형 AI 연동은 서버 기반이며 비용·실패 대체를 갖춘다.
- Figma를 필수 과정으로 두지 않는다. 기존 시안보다 더 좋은 화면을 Claude Code가 독립적으로 설계하고 실제 사용자 플로우와 함께 구현할 수 있다.

### 데이터 계약에서 표현할 최소 내용 (스키마·API명은 제안 사항)

| 엔티티 | 최소 정보 |
|---|---|
| cafeteria / layout | 식당 ID, 배치 버전, 실제/예시 구분, 입구·구역·브랜드 위치 및 기기 위치 |
| kiosks / queue snapshots | 내부 기기 ID, 위치 라벨, 대기 추정 인원, 처리시간 통계, ETA 범위, 품질, 관측 시각, 출처 |
| tables / table snapshots | 테이블 ID, 구역, 수용 정보(확인된 경우), 관측 상태, 품질, 갱신 시각 |
| brands / menus | 브랜드 ID, 이름, 코트 ID(확인 상태), 메뉴 ID, 이름, 확인된 가격·이미지·출처 |
| predictions | 대상, 시간 범위, 생성·예측 대상 시각, 예측 구간, 표본 수, 모델/방식, 품질, 데이터 모드 |
| order batches / orders | 묶음 ID, 브랜드별 고유 주문 ID, 표시 번호, 메뉴, 기기 ID, 주문 상태, 접수/완료 시각, 조회 토큰 해시/만료 |
| order events | 주문 ID, 상태 변화, 시각, 멱등 키 |
| demo sessions | 세션 ID, 출처 모드, 만료 시각, 격리된 상태 |
| notification subscriptions | 주문/세션 범위, 권한 및 수신 정보, 만료 (지원 시) |

- 데이터 출처는 최소한 `simulated`, `staged_live`, `recorded_inference`, `live` 등을 구별한다. 실제 학교 연동이 없으면 `live`(실제 현장)이라고 표시하지 않는다. 혼합 입력이라면 카드별 출처 표시.
- 오래된 스냅샷은 최신 정보처럼 보여주지 않는다. 관측 시각과 갱신 여부, 실패 상태를 전달한다. 서버 저장 시각과 KST 화면 시각을 일관되게 변환한다.
- 공개 데모 주문은 세션별로 격리하고 서버 측 쓰기 권한을 분리한다. 실제 결제정보/학교 계정/기존 CCTV 주소와 비밀번호/비밀 API 키를 공개 코드나 브라우저에 넣지 않는다. 만료·속도 제한·입력 검증·재접속·중복 방지·오류 처리를 갖춘다.

## 9. 디자인 방향 (구속력 있는 UX와 자유로운 스타일의 구분)

### 유지할 기준

- 단국대 학생이 자신의 캠퍼스 서비스라고 느낄 수 있게 한다. DKU 청색 정체성과 1947 COMMONS 실제 공간의 원목·화이트 인테리어에서 착안한다. FLOWEAT 자체 브랜드를 사용하고 공식 학교 서비스로 오인되지 않도록 학생 프로젝트/데모임을 표시한다.
- Apple: 주문 상태의 간결한 위계, Live Activities에서 착안한 실시간 상태 전달과 완료 인터랙션. 실제 OS Live Activities 구현을 의무화하지 않는다.
- 토스: 명확한 숫자, 가독성, 간결한 UX, 과도하게 분절되지 않는 정보 설계.
- Google Maps: 교통 혼잡처럼 직관적인 실시간 상태 표현과 위치 기반 안내. 실제 지도 레이아웃과 가독성에 따라 2D 또는 2.5D를 선택한다.
- 앱은 학생 중심의 상용 서비스 느낌을 목표로 하되 불필요한 채팅·장식·과도한 카드·긴 AI 설명을 피한다. 키오스크의 주문 절차와 메뉴 선택을 느리게 하지 않는다.

### Claude Code가 제안할 영역

색상·서체·로고·아이콘·레이아웃·내비게이션 구조·지도 스타일·모션·브레이크포인트·컴포넌트·기술 구현 방식을 자유롭게 설계한다. v1.0의 녹색 팔레트는 더 이상 기준이 아니며, 기존 파란색 Figma 시안도 최종 결과물로 고정하지 않는다. 제안은 사용자 가독성과 실제 동선에 근거한다.

학교 공식 심벌·마스코트·다른 앱의 로고 및 고유 이미지 등은 사용 허가와 라이선스를 확인한다. 디자인 패턴과 인터랙션은 적극 참고하되 실제 사진·영상·브랜드 자산을 무단으로 복제하거나 공식 제휴로 오인하게 하지 않는다.

## 11. 공모전 MVP 및 통합 시연 전략

### 실제 구현해야 하는 연결

1. 동의받은 연출 영상 또는 정당하게 사용 가능한 테스트 영상에서 모델을 실행하여 대기 영역과 테이블 상태를 분석한다.
2. 분석 결과가 화면 상태로 변환된다. 실시간 분석이 공개 데모에서 불안정하면 실제 추론 결과의 재생 모드를 별도 표기해 사용한다. 분석 코드와 모델 검증 기록은 유지한다.
3. 6개 기기 대기시간과 브랜드별 준비시간은 시연용 데이터로 실제 계산된다. 사용자가 시나리오를 변경하면 결과가 합리적으로 갱신된다.
4. 모의 키오스크에서 서로 다른 브랜드 메뉴를 주문한다. 실제 QR을 생성하고 다른 휴대폰으로 스캔한다.
5. 직원 화면에서 한 주문을 완료 처리하면 해당 주문만 학생 화면/공용 모니터에 반영된다. 두 번째 주문까지 별도로 완료 처리해 복수 주문 추적을 보여준다.
6. 학생은 완료 알림과 수령 브랜드를 확인하고, 최신 테이블 혼잡 상황을 확인한다. 실제 좌석 확보는 보장하지 않는다.

### 시연 모드 구분

- 연출 영상 추론: 실제 모델이 수행한 분석. 실제 단국대 현장 라이브가 아님.
- 실제 추론 결과 재생: 사전 영상 분석 결과를 시간순으로 재현. 재생 상태 표시.
- 모의 시스템/가상 주문 기록: 실제 주문·결제를 발생시키지 않고 서버 내 데이터를 생성. 시뮬레이션 표기.
- 실제 현장 연동: 학교·운영사·개인정보 관련 승인 및 데이터 확보 후에만 가능. 현재는 미확보.

공개 제출 URL에서 심사위원이 별도 학교 로그인 없이 체험할 수 있도록 하고, 학생용 화면과 데모 제어 화면을 구분한다. 운영자 데모는 격리된 자기 세션만 조작할 수 있게 한다. 실측 성능이나 실제 학교 도입이 확보되지 않았다는 이유로 UI만 만들어 가짜 동작을 시연하지 않는다.

## 12. 테스트·검증·완료 기준

아래는 개발 목표 및 평가 계획이지 측정된 성과가 아니다. 실제 기준값은 팀 환경을 고려해 계획 단계에서 확정한다.

| 검증 항목 | 검증 방식 |
|---|---|
| 핵심 사용자 여정 | 방문 전 정보 확인 → 기기 선택 → 모의 주문 → QR → 완료 알림 → 수령 안내, 다른 기기에서도 실제 작동. 10회 이상 반복 권장, 차단 오류 0건 목표 |
| 복수 주문 | 동일 결제의 두 브랜드 주문이 별도 상태를 유지. 한 주문 완료 시 나머지는 영향 없음. QR 중복 스캔/완료 중복 이벤트/만료/이미 완료된 QR/권한 분리 테스트 |
| 카메라 인식 | 수동 라벨과 대기열별 인원 추정 비교(MAE, 평균 절대 오차). 통행·가림·동행자 상황 별도 보고 |
| 테이블 인식 | 점유/비어 보임/불확실 라벨 비교. 특히 점유 상태를 빈 테이블로 오표시하는 비율 확인. 관측 범위 명시 |
| 주문 대기 예측 | 인원수만 사용한 기준선과 처리 속도 반영 모델 비교. 분 단위 오차 및 범위 포함률, 표본 수와 데이터 출처 보고 |
| 브랜드·메뉴 준비 예측 | 검증용 주문 기록의 실제 완료시간과 비교. 훈련/검증을 시간순 또는 적절하게 분리. 가상/실측 구분 |
| 단기 혼잡 예측 | 현재값 유지 기준선과 비교해 5~15분 뒤 오차 및 범위 포함률 평가. 검증할 데이터가 없으면 예측 미제공 |
| 완료 알림 | 다른 기기 간 화면 활성 상태 이벤트 전달 지연 기록(개발 목표 예: 2초 이내). 잠금화면/백그라운드는 실제 지원·권한 기기에서 별도 확인 |
| 생성형 AI(채택 시) | 존재하지 않는 숫자·상태·근거 생성 방지, 장애/비용 제한 시 대체 동작, 개발 과정 AI 활용 기록 |
| 데이터 신뢰성 | 가림·오프라인·오래된 데이터·낮은 신뢰도·모드 전환·오류 시 안전한 표현 |
| UI/UX | iOS/Android/데스크톱에서 모바일 핵심 흐름, 지도 방향 이해, 큰 메뉴 목록 검색, 접근성 및 성능 확인 |

### 학생 대상 사용자 검증

학생 6~10명 정도의 소규모 검증을 권장하되 일정에 맞춰 조정한다. 혼밥/동반 식사와 여러 학과 이용자를 포함하려 노력한다. 참가자에게 제안된 프로토타입과 비교 상황임을 알린다.

- 공용 모니터로 확인하는 경우와 개인 알림의 확인 횟수, 놓친 완료번호, 불필요한 이동 여부 비교.
- 줄 길이만 보이는 상황과 대기시간·배치도가 제공되는 상황에서 선택 시간 및 선택한 줄의 예상/시뮬레이션 대기 비교.
- 방문 전 혼잡·메뉴 정보 이해 여부, 해당 정보로 달라진 선택, 재사용 의향, QR 스캔과 알림 설정 불편 확인.
- 실내 지도에서 학생이 실제 위치를 직관적으로 이해할 수 있는지 확인한다. 부정확한 배치도라면 실사용 효과 검증이 아니라 시안 테스트라고 표시한다.

대기열 분산 효과를 시뮬레이션으로 비교할 경우 동일한 유입·처리시간 조건을 유지하고 안내를 따르는 비율을 바꿔본다. 좋은 결과만 선택하지 않고 평균/최대 대기, 줄 편차, 처리량 및 좌석 제약을 함께 본다. 실제 현장 혼잡 감소율로 일반화하지 않는다.

## 13. 실제 도입 가능성과 남은 확인 사항

| 확인 대상 | 의미 | 현재 상태 |

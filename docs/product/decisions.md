# 설계 결정 기록 (ADR)

새 결정은 아래에 추가합니다. 바뀐 결정은 지우지 않고 "대체됨"으로 표시합니다.

## D-001 · Next.js 단일 구조, 추가 비용 0원 (2026-11-24, 승인됨)
- 프론트엔드와 API를 Next.js 16 앱 하나로. 별도 상시 서버·유료 DB·유료 LLM API 없음. 배포는 Vercel Hobby.
- 도메인 로직은 `src/core`의 순수 TypeScript. 브라우저와 서버가 같은 코드를 실행.

## D-002 · 저장소는 포트/어댑터, DB 없이 시작 (2026-11-24)
- `OrderRepository`·`ChangeFeed` 포트. 어댑터: `memory`(서버 프로세스), `device`(localStorage + BroadcastChannel).
- Vercel 서버리스는 인스턴스 간 메모리를 공유하지 않으므로 `FLOWEAT_STORE=none`이 자동 적용되고, 클라이언트는 한 기기 체험 모드로 전환.
- 공용 저장소가 필요해지면 무료 후보(Upstash Redis via Vercel Marketplace 등)를 보고하고 승인 후 어댑터 1개를 추가.

## D-003 · 실시간 전달은 SSE 대신 롱폴링 (2026-11-24)
- 서버리스·프록시 호환성과 어댑터 교체 용이성 때문. 변경이 생기면 즉시 응답, 없으면 20초 후 재요청.
- 측정: 로컬 기기 간 완료 반영 124ms (E2E).

## D-004 · 식당 상태는 결정적 시뮬레이션 (2026-11-24)
- (날짜, 시나리오, 시각) → 같은 결과. 저장소 없이 모든 기기가 같은 상태를 봄.
- 실제 시각이 점심(11:00–13:50 KST)이면 그 시각을, 아니면 11:50–12:50 피크를 60분 주기로 반복.

## D-005 · 영상 모델: YOLOX-Nano 기본, Tiny 선택 (2026-11-24)
- 후보: YOLOX-Nano/Tiny(Apache-2.0, 가중치 배포 조건 명확), YOLO11n(AGPL-3.0, 저장소 공개 의무 발생 가능), NanoDet-Plus(Apache-2.0, 디코딩 별도 구현 필요), SSD-MobileNet(정확도 낮음).
- 테스트 영상 라벨 평가에서 Nano가 Tiny와 같거나 높고, 5.5배 작고 2–4배 빠름 → 브라우저 기본. 검출기는 `MODELS` 레지스트리로 교체 가능.

## D-006 · 서비스 내 생성형 AI 런타임 호출 제외 (2026-11-24)
- 사유: 추가 비용 0원 원칙. PRD 6.5의 "런타임 적용이 곤란하면 사유와 충족 근거를 기재" 조항에 따름.
- 대신: ① 메뉴 119행 조리 유형 분류를 Claude Code로 작성(사람 검수 대상, `data/menu-classification.json`) ② 상황 한 줄은 검증된 숫자만 넣는 규칙 템플릿(`src/core/insight.ts`), 문구는 생성형 AI로 다듬음 ③ 전체 개발을 Claude Code로 진행하고 기록(`docs/dev-log/`).
- 브라우저 내장 LLM·WebLLM은 지원 기기가 제한적이고 모델 다운로드가 커서 제외.

## D-007 · 지도는 2D "정문 시점" (2026-11-24)
- 확인된 관계(정문, 좌우 3대, 바깥쪽 줄)만 그림. 실측이 없는 상태의 2.5D/3D는 존재하지 않는 형상을 만들어 내므로 보류. 평면도 확보 시 재검토(R14).

## D-008 · 줄 추천 대신 "비슷함" 묶음 (2026-11-24)
- 가장 빠른 줄과의 차이가 max(60초, 25%) 이내면 같이 강조. 한 줄로 몰리는 것을 막고 PRD의 "강제 이동 금지"를 지킴.

## D-009 · 테이블은 보수적으로 (2026-11-24)
- 사람이 안 보여도 8초간 "사용 중" 유지, 서 있는 사람에 가려지면 "판단 어려움". 사용 중인 자리를 빈자리로 보이게 하는 오류를 최우선으로 줄임(평가 0%).

## D-010 · 디자인 v2 "Commons Floor" (2026-11-25, 승인됨)
- v1 카드 목록 + 도식 지도를 대체. 2.5D 정문 시점 지도가 홈의 중심이고, 정보는 지도 위로 올라오는 시트와 레이어 탭으로.
- 지도 기울기는 90/62/45/64/70°를 같은 데이터로 비교해 68° 선택. 확인 안 된 공간은 안개로.
- 근거: `docs/design/reference-review-v2.md`, 전후 비교 `docs/design/compare/`.

## D-011 · 경로 구조 (2026-11-25)
- `/` = 심사 단일 진입 화면, `/app/*` = 학생 앱, `/o/{token}` = QR 랜딩(짧은 주소 유지), `/demo` → `/`.

## D-012 · 다중 줄 분석과 판정 기준점 (2026-11-25)
- 키오스크마다 이용 구역·대기 구역 쌍. 주문 중(가장 오래 머문 1명)/동행/대기/지나감 구분. 기준점은 장면별(머리/발/중심), 속도는 사람 키 기준.

## D-013 · 카메라 위치 권장: 줄을 비스듬히 (2026-11-25)
- 같은 사람·같은 시뮬레이션의 합성 영상 비교에서 비스듬한 카메라가 정면보다 대기 오차·이용 기록·이용 시간 모두 우수. 실제 설치 위치는 미확정이며 운영 협의 대상.

## D-014 · 자리 라벨 정의 변경 (2026-11-25)
- "앉아 있음"만으로는 학생에게 필요한 '앉을 수 있나'를 평가할 수 없어 3분류(앉음/맡음·잠깐 비움/비어 있음)로 재정의. 핵심 지표는 '이용할 수 없는 자리를 빈자리로 보여 준 비율'.

## D-015 · 분할 체험은 화면 크기별 배치 (2026-11-25)
- 휴대폰은 탭 전환 + 단계 안내 + 자동 전환, 태블릿은 학생 화면 고정 + 나머지 전환, 데스크톱은 4개 동시. “PC로 접속하세요” 안내로 대체하지 않음.
- 4개 화면은 계속 실제 페이지(iframe)라 같은 저장소를 공유. 배치를 바꿀 때 iframe을 다시 만들지 않음.

## D-016 · 추론 실행 방식은 측정으로 선택 (2026-11-25)
- WASM이 기준. WebGPU는 하드웨어 어댑터 + 준비 시간 제한 + WASM보다 20% 이상 빠를 때만. 결과는 기기별 캐시, 실행 중 저하·오류 시 WASM 전환.
- 근거: 실제 배포 검수에서 소프트웨어 WebGPU가 프레임당 3.9초, WASM은 44ms.

## D-017 · 실제 체험 주문과 시뮬레이션 표기 (2026-11-25)
- 모니터: 체험 주문 번호는 진하게, 시뮬레이션 손님 번호는 흐리고 작게 + 범례. 학생 앱 시각 칩은 “시뮬레이션 hh:mm”, 주문 카드는 “키오스크 체험 주문”.
- 매장 표식은 실제 로고·색이 아닌 중립 글자 타일(권리 없는 브랜드 자산 미사용).

# 설계 결정 기록 (ADR)

새 결정은 아래에 추가합니다. 바뀐 결정은 지우지 않고 "대체됨"으로 표시합니다.

## D-001 · Next.js 단일 구조, 추가 비용 0원 (2026-11-24, 승인됨)
- 프론트엔드와 API를 Next.js 16 앱 하나로. 별도 상시 서버·유료 DB·유료 LLM API 없음. 배포는 Vercel Hobby.
- 도메인 로직은 `src/core`의 순수 TypeScript. 브라우저와 서버가 같은 코드를 실행.

## D-002 · 저장소는 포트/어댑터, DB 없이 시작 (2026-11-24)
- `OrderRepository`·`ChangeFeed` 포트. 어댑터: `memory`(서버 프로세스), `device`(localStorage + BroadcastChannel).
- Vercel 서버리스는 인스턴스 간 메모리를 공유하지 않으므로 `FLOWEAT_STORE=none`이 자동 적용되고, 클라이언트는 한 기기 체험 모드로 전환.
- 공용 저장소가 필요해지면 무료 후보(Upstash Redis via Vercel Marketplace 등)를 보고하고 승인 후 어댑터 1개를 추가.

## D-003 · 실시간 전달은 SSE 대신 롱폴링 (2026-11-24)
- 서버리스·프록시 호환성과 어댑터 교체 용이성 때문. 변경이 생기면 즉시 응답, 없으면 20초 후 재요청.
- 측정: 로컬 기기 간 완료 반영 124ms (E2E).

## D-004 · 식당 상태는 결정적 시뮬레이션 (2026-11-24)
- (날짜, 시나리오, 시각) → 같은 결과. 저장소 없이 모든 기기가 같은 상태를 봄.
- (2026-11-25 변경) 기본은 그날 시뮬레이션에서 줄이 가장 긴 45분(11:20–13:30 안)을 반복(`peakLoopStart`). 실제 KST 시각 연동은 선택(`?clock=real`, 체험 홈 토글) — 점심 11:00–13:50에만 실제 시각 사용.

## D-005 · 영상 모델: YOLOX-Nano 기본, Tiny 선택 (2026-11-24)
- 후보: YOLOX-Nano/Tiny(Apache-2.0, 가중치 배포 조건 명확), YOLO11n(AGPL-3.0, 저장소 공개 의무 발생 가능), NanoDet-Plus(Apache-2.0, 디코딩 별도 구현 필요), SSD-MobileNet(정확도 낮음).
- 테스트 영상 라벨 평가에서 Nano가 Tiny와 같거나 높고, 5.5배 작고 2–4배 빠름 → 브라우저 기본. 검출기는 `MODELS` 레지스트리로 교체 가능.

## D-006 · 서비스 내 생성형 AI 런타임 호출 제외 (2026-11-24)
- 사유: 추가 비용 0원 원칙. PRD 6.5의 "런타임 적용이 곤란하면 사유와 충족 근거를 기재" 조항에 따름.
- 대신: ① 메뉴 119행 조리 유형 분류를 Claude Code로 작성(사람 검수 대상, `data/menu-classification.json`) ② 상황 한 줄은 검증된 숫자만 넣는 규칙 템플릿(`src/core/insight.ts`), 문구는 생성형 AI로 다듬음 ③ 전체 개발을 Claude Code로 진행하고 기록(`docs/dev-log/`).
- 브라우저 내장 LLM·WebLLM은 지원 기기가 제한적이고 모델 다운로드가 커서 제외.

## D-007 · 지도는 2D "정문 시점" (2026-11-24) — 일부 대체됨 (D-022)
- 확인된 관계(정문, 좌우 3대, 바깥쪽 줄)만 그림. 실측이 없는 상태의 2.5D/3D는 존재하지 않는 형상을 만들어 내므로 보류. 평면도 확보 시 재검토(R14).

## D-008 · 줄 추천 대신 "비슷함" 묶음 (2026-11-24)
- 가장 빠른 줄과의 차이가 max(60초, 25%) 이내면 같이 강조. 한 줄로 몰리는 것을 막고 PRD의 "강제 이동 금지"를 지킴.

## D-009 · 테이블은 보수적으로 (2026-11-24)
- 사람이 안 보여도 잠깐(2.5초 + 자리 비움 3.5초) "사용 중" 유지, 가방은 맡은 자리, 가려지면 최대 6초 이전 상태 유지 후 "판단 어려움"(2026-11-25 코드 기준으로 수치 정정). 사용 중인 자리를 빈자리로 보이게 하는 오류를 최우선으로 줄임.

## D-010 · 디자인 v2 "Commons Floor" (2026-11-25, 승인됨)
- v1 카드 목록 + 도식 지도를 대체. 2.5D 정문 시점 지도가 홈의 중심이고, 정보는 지도 위로 올라오는 시트와 레이어 탭으로.
- 지도 기울기는 90/62/45/64/70°를 같은 데이터로 비교해 68° 선택. 확인 안 된 공간은 안개로.
- 근거: `docs/design/reference-review-v2.md`, 전후 비교 `docs/design/compare/`.

## D-011 · 경로 구조 (2026-11-25)
- `/` = 심사 단일 진입 화면, `/app/*` = 학생 앱, `/o/{token}` = QR 랜딩(짧은 주소 유지), `/demo` → `/`.

## D-012 · 다중 줄 분석과 판정 기준점 (2026-11-25)
- 키오스크마다 이용 구역·대기 구역 쌍. 주문 중(가장 오래 머문 1명)/동행/대기/지나감 구분. 기준점은 장면별(머리/발/중심), 속도는 사람 키 기준.

## D-013 · 카메라 위치 권장: 줄을 비스듬히 (2026-11-25) — **대체됨 (D-018)**
- 같은 사람·같은 시뮬레이션의 합성 영상 비교에서 비스듬한 카메라가 정면보다 대기 오차·이용 기록·이용 시간 모두 우수. 실제 설치 위치는 미확정이며 운영 협의 대상.

## D-014 · 자리 라벨 정의 변경 (2026-11-25)
- "앉아 있음"만으로는 학생에게 필요한 '앉을 수 있나'를 평가할 수 없어 3분류(앉음/맡음·잠깐 비움/비어 있음)로 재정의. 핵심 지표는 '이용할 수 없는 자리를 빈자리로 보여 준 비율'.

## D-015 · 분할 체험은 화면 크기별 배치 (2026-11-25)
- 휴대폰은 탭 전환 + 단계 안내 + 자동 전환, 태블릿은 학생 화면 고정 + 나머지 전환, 데스크톱은 4개 동시. “PC로 접속하세요” 안내로 대체하지 않음.
- 4개 화면은 계속 실제 페이지(iframe)라 같은 저장소를 공유. 배치를 바꿀 때 iframe을 다시 만들지 않음.

## D-016 · 추론 실행 방식은 측정으로 선택 (2026-11-25)
- WASM이 기준. WebGPU는 하드웨어 어댑터 + 준비 시간 제한 + WASM보다 20% 이상 빠를 때만. 결과는 기기별 캐시, 실행 중 저하·오류 시 WASM 전환.
- 근거: 실제 배포 검수에서 소프트웨어 WebGPU가 프레임당 3.9초, WASM은 44ms.

## D-017 · 실제 체험 주문과 시뮬레이션 표기 (2026-11-25)
- 모니터: 체험 주문 번호는 진하게, 시뮬레이션 손님 번호는 흐리고 작게 + 범례. 학생 앱 시각 칩은 “시뮬레이션 hh:mm”, 주문 카드는 “키오스크 체험 주문”.
- 매장 표식은 실제 로고·색이 아닌 중립 글자 타일(권리 없는 브랜드 자산 미사용).

## D-018 · 대기 인원 집계는 혼합(v3), 카메라 위치는 미정 (2026-11-25, 독립 검수 반영)
- 독립 검수에서 단순 구역 집계가 v2보다 MAE가 낮다는 지적 → 재현. 개발 시드 4개로 방식·파라미터를 정하고(결정 규칙: 통행자 오인 ≤10% 중 MAE 최소) 새 홀드아웃 시드 4개로 한 번 평가.
- 홀드아웃 MAE: 단순 0.231 / v2 0.277 / **v3 0.191**, 통행자 오인 68.9% / 0.6% / 5.9%. v3 채택.
- 카메라: 정면은 인원·통행자 구분, 비스듬히는 주문 중 판정·처리시간이 나음 → D-013의 “모든 지표 우수”는 철회, 현장 촬영 비교 후 결정.

## D-019 · 노트북 서버 모드의 역할 구분 (2026-11-25)
- 학생 = QR 토큰, 키오스크 = 누구나 주문(요청 제한), 직원 = 세션별 직원 키, 운영자 = 운영자 키(세션 초기화·직원 키 발급). 세션 코드만으로는 완료·초기화 불가.
- 요청 제한은 X-Forwarded-For(노트북 서버에서 위조 가능)에 의존하지 않도록 클라이언트·전체·세션 3중 버킷.
- Vercel 공개 배포는 공용 저장소가 없어 쓰기 API가 꺼져 있고, 한 기기 체험 모드는 브라우저 안에서만 동작.

## D-020 · 시뮬레이션 가정의 분리와 상한 (2026-11-25)
- 모든 시뮬레이션 가정을 `src/core/data/calibration.json`으로 분리(현장 측정값으로 교체 가능). 피크 수요가 키오스크 처리 용량을 넘어 줄이 최대 28명/키오스크, 134명까지 쌓이던 문제 → 도착률 재설정, 상한을 단위 테스트로 고정.

## D-021 · 현장 메뉴 관측 병합 (2026-11-25, 현장 자료 반영)
- 실제 키오스크 영상(2026-11-25)에서 읽은 89행 + 손에 가린 2행을 기존 제3자 목록 119행과 병합 → 127개. 이름·가격이 화면과 같으면 `priceBasis: "field"`, 새로 본 8개는 `field_only`, 못 본 36개는 `reference`(참고 가격). 가격 충돌 0건.
- ‘준비중’은 촬영 순간의 표시(`field.display = "preparing"`)로만 저장. 품절·실시간 판매 상태로 쓰지 않음. 키오스크의 ‘준비중’ 타일은 날짜별 임의 시연 표시(`demoPreparing`)로 따로 만들고 그렇게 표기.
- 매장 순서는 실제 키오스크 탭 순서(2줄×5). 탭 순서는 카운터 순서가 아님.
- 재현: `python3 scripts/data/merge_field_menu.py` (멱등). 원본 사진·영상은 저장소에 넣지 않음(`.gitignore`).

## D-022 · 지도: 정문 안내도 기반 홀 구조 (2026-11-25)
- 정문 유리의 ‘혜당관 1F’ 안내도 사진으로 홀 외곽, 안쪽 노란 매장 구역(바비든든·포포420·중식대장→가오슝 추정·폭풍분식·값찌개·경성카츠), 오른쪽 파란 구역(뽀까뽀까=현재 미확인·51장국밥·잘린 부분), 카페1847·화장실·계단을 그림.
- 축척: 안내도 픽셀 × 0.05. 이 값에서 안내도의 키오스크 표시가 사용자 확인 키오스크 위치(축에서 ±5)와 맞음. 실측이 아님을 지도와 데이터에 표기.
- 최신 현장 우선: 안내도의 중식대장·뽀까뽀까는 현재 매장으로 쓰지 않음. 가오슝은 현장 사진(폭풍분식 옆)으로 ‘추정’, 비비고고·도쿄야·광뚝은 잘린 오른쪽 구역의 ‘위치 미확정’.
- ‘주문 줄’ 탭은 기존처럼 키오스크 중심, ‘자리’·‘수령’ 탭은 홀 전체로 카메라가 이동. 좌석 배치·모니터 위치·카메라 위치는 그리지 않음.

## D-023 · 직원 화면 = 번호 입력 호출기, KDS는 보조 (2026-11-25)
- 현장 확인: 음식이 준비되면 직원이 전용 기기에 번호를 누르고 공용 모니터에 표시. → `/staff`를 번호 입력 호출기로 바꿈(매장 선택 → 번호 → 호출). 추가 업무 없음.
- 서버: `POST /api/sessions/{sid}/call {brandId, number}` — (세션, 매장, 번호)로만 찾음. 결과 `called / already_ready / already_closed / not_found / invalid`. 직원 키 필요(D-019 유지). 같은 번호 동시 호출 6건 → 1건만 변경(단위 테스트).
- 호출 취소 10초(기존 되돌리기 재사용). 기존 KDS는 `/staff/board` 보조 화면.
- 실제 기기의 모양·버튼·통신 방식은 모름 → 같은 역할만 재현한다고 표기.

## D-024 · 호출 모니터: 현장 2화면 구조 (2026-11-25)
- 사진의 하늘색 ‘주문 번호 리스트’ 2대: 화면 1 = (잘림, 바비든든 추정)·포포420·가오슝·폭풍분식·값찌개, 화면 2 = 경성카츠·도쿄야·51장국밥·광뚝·비비고고. 브랜드 열 아래 번호를 세로로.
- 실제 빨간/검은 번호의 뜻은 모름 → 빨간색은 ‘30초 안에 호출된 번호’라는 FLOWEAT 시연 규칙으로만 쓰고 화면에 그렇게 적음. `?screen=A|B`로 TV 1대씩.

## D-025 · 시연 폴리싱: 호출 취소 10초 유지 (2026-11-26)
- 호출 취소 창은 서버 규칙(OrderService.undoReady, 10초) 그대로 둠. 줄이면 직원 실수 복구가 어렵고, 늘리면 학생이 받은 알림이 오래 뒤집힐 수 있음.
- 대신 호출 직후 상태 배너 안에 ‘호출 취소 N초’ 버튼을 카운트다운과 함께 보여 줌(전에는 토스트가 6초에 사라져 남은 시간이 안 보였음). 보안·주문 로직 변경 없음.
- 1440×900 분할 데모에서 호출기 키패드·호출 버튼이 잘리던 문제: 낮은 화면(`short`, `short-wide` 변형)에서 키패드가 남은 높이를 채우고, 넓고 낮은 화면은 2열(번호·상태 | 키패드)로.

## D-026 · 지도: 숫자는 목록에만, 지도는 위치와 흐름 (2026-11-26)
- 지도 위 예상시간 칩을 없앰(아래 6칸 목록과 같은 숫자 반복, 확대 버튼과 겹침). 지도는 키오스크 위치 핀·줄 사람 점·선택 강조만.
- 키오스크 = 원형 핀 + 화면 아이콘(배터리처럼 보이던 직사각형+검은 띠 대체). 빠른 줄은 파란 핀.
- ‘흐름선’(FLOWEAT 고유 요소): 정문 → 선택한(또는 뚜렷이 빠른) 줄의 맨 뒤, 수령 탭에서는 정문 → 내 카운터. 장식이 아니라 길 안내.
- 추천 과장 방지: 빠른 줄이 5~6곳이면 아무 줄도 강조하지 않고 ‘어느 줄이든 비슷해요’. 1곳이면 위치 이름, 2~4곳이면 ‘파란 줄 N곳이 비슷해요’.
- 확대 버튼은 화면 가운데(빈 통로)가 아니라 선택한 줄·추천 줄·내 카운터 쪽으로 확대. 되돌리기 아이콘은 별 → 화면 맞춤 모서리.
- 벽은 두께 있는 선으로, 정문은 벽의 틈으로. 안내도 오른쪽 잘린 부분은 기존처럼 흐리게. 식사 공간에는 ‘좌석 배치 미표시’ 라벨만.

## D-027 · 좌석 탭: 지도 대신 단위별 격자 (2026-11-26)
- 좌석 배치는 확인 전이라 지도에서 보여 줄 게 없음 → 폰 좌석 탭은 지도를 빼고 바로 정보.
- ‘여럿이라면(4인 테이블)’·‘혼자라면(1인석)’ 두 숫자를 맨 위에. 격자 칸은 모양으로 구분: 1인석 = 의자(등받이+방석), 4인 테이블 = 의자 4개 붙은 테이블(영화관·주차장 좌석표 방식).
- ‘빈 자리’ → ‘비어 보임’, 상단에 ‘추정치 · 자리 위치는 표시하지 않아요’, 아래에 ‘칸 순서는 실제 자리 순서가 아니에요’. 인원 선택기는 넣지 않음(두 숫자로 충분, 새 기능 최소화).

## D-028 · 키오스크 메뉴 타일: 텍스트 우선 (2026-11-26)
- 비교: (A) 큰 일러스트 타일(이전) — 사진처럼 보이지만 정보가 없음, 자리만 차지 / (B) 텍스트 목록 — 가장 빠르게 읽힘, 실제 키오스크 느낌은 약함 / (C) 생성 이미지·사진 — 사용권·실물과 다를 위험, 제외.
- 선택: 폰은 B(가로 행: 작은 아이콘 + 이름·가격·조리시간), 태블릿 이상은 A를 줄인 형태(아이콘 띠 2:1, 이름 16px 굵게, 가격 굵게, ‘조리 N–M분’ 명시).
- 폰 장바구니는 한 줄 바(개수·합계·결제)로 접고 ‘담은 메뉴’로 펼침(화면 40% → 약 20%). 시작 화면 매장 목록은 누르면 그 매장 메뉴로 바로 가는 버튼. 영수증 화면은 내용 묶음을 세로 가운데로.

## D-029 · 수령 탭 목록 ↔ 지도, 영상 AI 화면 (2026-11-26)
- 수령 목록의 행을 누르면 지도에 그 매장 카운터·흐름선 표시(폰은 지도가 보이도록 위로 스크롤). 메뉴 보기는 행 오른쪽 별도 ‘메뉴 >’ 링크로 분리. 위치 미확정 매장은 후보 칸에 ‘후보’ 표시.
- /ops를 앱과 같은 디자인 체계로: 상단 5단계(영상 입력 → 사람 검출 → 대기열·좌석 계산 → 예상시간 → 학생 앱 반영)에 현재 값, 영상 중심, ‘미리 계산한 결과 재생 / 이 브라우저에서 실시간 추론’ 분리 표시, ‘학생 앱에서 보기’ 버튼, 모델·성능 지표는 접힘. 알고리즘·평가 결과는 바꾸지 않음.
